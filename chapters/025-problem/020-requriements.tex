Based on the past sections, the requirements for the software developed are documented in the listings below, separating them into functional and non-functional requirements as described in \cite{braunNichtfunktionaleAnforderungen2016}.

\subsection{Functional Requirements}
The following listing documents the functional requirements, ordered by priority.

\begin{itemize}
	\item \textbf{F1 - Inventory management:}
	      The inventory for Ansible needs to be defined using Kubernetes objects, representing \texttt{Groups} and \texttt{Hosts} respectively, including their respective variables.
	\item \textbf{F2 - \texttt{Playbook} sources:}
	      \texttt{Playbooks} need to be pulled from Git or specified in the Kubernetes object responsible. This should also allow pinning to specific branches or tags on git repositories.
	\item \textbf{F3 - \texttt{Playbook} execution scheduling:}
	      \texttt{Playbook} execution needs to be schedulable on a regular interval. Additionally, there should be some way of running \texttt{Playbooks} ad-hoc.
	\item \textbf{F4 - Status reporting:}
	      After execution, the status of the last run needs to be reported back to the objects in Kubernetes.
	\item \textbf{F5 - Bootstrap management:}
	      The operator needs to bootstrap and manage itself without requiring human interaction, allowing for manifest management entirely via git.
\end{itemize}

\subsection{Non-Functional Requirements}
The listing below documents the non-functional requirements, again ordered by priority.

\begin{itemize}
	\item \textbf{N1 - RBAC support:}
	      The operator must support Kubernetes \gls{rbac}, and use it itself to restrict the \texttt{ServiceAccount} capabilities.
    \item \textbf{N2 - Host key checking:}
          The operator needs to perform \gls{ssh} authentication with host key checking. If no key exists, it should perform \gls{tofu}.
	\item \textbf{N3 - Runner restriction:}
	      The environment for the runner should be heavily restricted, dropping all capabilities and using a restricted execution policy, as well as scheduling runs as non-root.
    \item \textbf{N4 - Reconciliation best practices:}
          Reconciliation should be idempotent. Reconcile errors should result in a retry of the reconcile cycle. Deleting a managed resource must not leave behind any objects managed by that resource.
    \item \textbf{N5 - Credential management:}
          Credentials can never be inlined into custom resources, and must always be stored in Kubernetes \texttt{Secrets}.
\end{itemize}

These requirements will serve as the basis for the architecture and the implementation of the solution.

Ansible, in contrast to Kubernetes' declarative approach, it uses scripts called playbooks to describe the target state of the machine, which are usually held idempotent to ensure that re-running the same playbook doesn't alter the state of the target machine if it already is in the requested state.
This section is going to give an introduction to Ansible and it's components to give a good understanding for how Ansible works and what it's requirements for execution are.
The section will only focus on components that are going to be relevant to the implementation of the operator, so components that will be purposefully omitted as per scope definition will already be omitted here.

\subsection{The Ansible inventory}
The Ansible inventory is what tells Ansible what hosts to target, how they are grouped and what variables to use for them when evaluating playbooks or roles.
It is written in a file or a predetermined directory structure, however this thesis will use the \gls{yaml} format with the directory layout for declaring the inventory, for easier manageability of scaling environments, as per \cite{ansibleinventoryintro}.

An Ansible inventory is separated into \texttt{Groups} and \texttt{Hosts}, both of which can have variables.
\texttt{Groups} are a way to \texttt{Group} multiple \texttt{Hosts} into a logical unit, which can be targeted by a playbook, as we will see in a later section.
A \texttt{Group} is declared simply by creating a key in the YAML file that represents the inventory at root level.
\texttt{Groups} may also have subgroups, which in turn makes the parent \texttt{Group} into a \enquote{metagroup}.
\parencite{ansibleinventoryintro}

The individual \texttt{Hosts} are then declared as children of a specific Ansible \texttt{Group}.
These \texttt{Hosts} need to have at least a name and hostname, so Ansible can access them.
Ansible will default to the declared inventory name as hostname if no hostname is specified.

The format for specifying an inventory can be found below, sourced from \cite{ansibleinventoryintro}:

%TC:ignore
\begin{lstlisting}[language=yaml,caption=Example Ansible inventory with groups and hosts (source: \cite{ansibleinventoryintro})]
leafs:
  hosts:
    leaf01:
      ansible_host: 192.0.2.100
    leaf02:
      ansible_host: 192.0.2.110

spines:
  hosts:
    spine01:
      ansible_host: 192.0.2.120
    spine02:
      ansible_host: 192.0.2.130

network:
  children:
    leafs:
    spines:

webservers:
  hosts:
    webserver01:
      ansible_host: 192.0.2.140
    webserver02:
      ansible_host: 192.0.2.150

datacenter:
  children:
    network:
    webservers:
\end{lstlisting}
%TC:endignore

The listing shows an inventory file declaring the \texttt{Groups} leafs, spines, network, webservers and datacenter, with the corresponding hosts.
Notably spines and leafs are subgroups of network, and network and webservers are subgroups of datacenter.

\subsection{Ansible playbooks}
A \texttt{Playbook} in Ansible is a file that contains several \texttt{Plays}, which in turn contain \texttt{Tasks} to perform on a target.
The \texttt{Tasks} here are operations like copying a file or setting the timezone for a host. Each of those, depending on the nature, is usually idempotent.
The playbook below is an example of how one could manage webservers and database servers using an ansible playbook:

%TC:ignore
\begin{lstlisting}[language=yaml,caption=Ansible playbook example (source: \cite{ansibleplaybooks})]
---
- name: Update web servers
  hosts: webservers
  remote_user: root

  tasks:
  - name: Ensure apache is at the latest version
    ansible.builtin.yum:
      name: httpd
      state: latest

  - name: Write the apache config file
    ansible.builtin.template:
      src: /srv/httpd.j2
      dest: /etc/httpd.conf

- name: Update db servers
  hosts: databases
  remote_user: root

  tasks:
  - name: Ensure postgresql is at the latest version
    ansible.builtin.yum:
      name: postgresql
      state: latest

  - name: Ensure that postgresql is started
    ansible.builtin.service:
      name: postgresql
      state: started
\end{lstlisting}
%TC:endignore
This playbook contains two \texttt{Plays} which target the \texttt{Groups} webservers and databases respectively. On webservers, they ensure the httpd package is installed with the latest version, and then write the configuration for it to \enquote{/etc/httpd.conf}, templating it from a local template file.
The second \texttt{Play} targets the databases and ensures PostgreSQL is installed and started.
\parencite{ansibleplaybooks}

\subsection{Ansible roles}
\texttt{Roles} are reusable units of \texttt{Tasks} which we can use in Ansible to split configurations into reusable chunks to, for example, apply a similar configuration repeatedly to several logicial targets without having to contain them in playbooks.
\texttt{Roles} also allow for easy delivery of templates and other files together with these tasks.
Once created, \texttt{Roles} can be referenced either in \texttt{Playbooks} or within other roles as dependencies.
Roles that are required for the execution of a playbook can be declared in a file called \enquote{requirements.yml} which can in turn be used to install all roles listed in the file.
\parencite{ansibleroles, ansiblegalaxyuserguide}

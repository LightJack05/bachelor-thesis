This section shows the exact specifications for the \glspl{crd} implemented, how they are validated and how their fields affect the resources.
The fields shown here will be limited to the spec part of the resource.
Fields in the status block shall, if necessary, be explained in the following section.
In the light of promise theory, every resource here can be thought of as a promise to the user, specifying behavior of the operator.
Kubernetes in this case acts as the platform, forwarding the promise of the operator made with its \gls{crd} to the user of the cluster.

\subsection{API Version in Kubernetes}

In order to implement an \gls{api} in Kubernetes, there needs to be separation between resources, versioning and naming of the resources.
Kubernetes groups objects into \enquote{API versions}, which consist of an identifier for the \gls{api} as well as a version itself.
In this case, the \enquote{ansible-operator.lightjack.de/v1alpha1} \gls{api} version was created.
Here, the \enquote{v1alpha1} indicates the first version of the operator \enquote{v1} with an alpha state resource \enquote{alpha} in the first version \enquote{1}.
Should there be breaking changes to the \gls{api} once the operator is in a stable condition, this version will be changed and the resources moved to a different \gls{api} version.

\subsection{The \anhost resource}
The complete \anhost spec type declaration can be found in the appendix under section \ref{app:anhostdeclare}.

A \anhost may be defined as follows:

%TC:ignore
\begin{lstlisting}[language=yaml,caption=Example \anhost definition]
apiVersion: ansible-operator.lightjack.de/v1alpha1
kind: AnsibleHost
metadata:
  name: ssh-node-1
spec:
  ansibleName: ssh-node-1
  connection:
    host: ssh-node-1.default.svc.cluster.local
    user: ansible
  ssh:
    sshKeySecretRef:
      name: ansible-operator-hosts-private-key
    sshHostKeySecretRef:
      name: ssh-node-1-host-key
    ignoreHostKey: false
  privilege:
    become: true
\end{lstlisting}
%TC:endignore

One notable variable is the \enquote{AnsibleName} which is used to specify the name of the resource within the Ansible inventory.
The \enquote{ignoreHostKey} option is used to disable getting and enforcing the \gls{ssh} host key.


\subsection{The \angroup resource}
The complete \angroup spec type declaration can be found in the appendix under section \ref{app:angroupdeclare}.

An \angroup may be defined as follows:

%TC:ignore
\begin{lstlisting}[language=yaml,caption= Example \angroup definition]
apiVersion: ansible-operator.lightjack.de/v1alpha1
kind: AnsibleGroup
metadata:
  name: group-web-tier
spec:
  ansibleName: web_tier
  hosts:
    - name: ssh-node-1
    - name: ssh-node-2
  groups: []
  groupVars: |
    http_port: 80
    max_clients: 200
\end{lstlisting}
%TC:endignore

This manifest would create an \angroup resource which has no \texttt{Groups} as subgroups, and contains \enquote{ssh-node-1} and \enquote{ssh-node-2} as \texttt{Hosts}.
It also injects the variables \enquote{http\_port} and \enquote{max\_clients} as \texttt{Group} variables.

\subsection{The \anplaybook resource}
The complete \anplaybook spec type declaration can be found in the appendix under section \ref{app:anplaybookdeclare}.
The \anplaybook struct contains two mutually exclusive values, \enquote{AnsiblePlaybookInline} and \enquote{AnsiblePlaybookGit}, which are therefore declared as pointers.
Mutual exclusivity is enforced via a \gls{cel} statement wrapped in a kubebuilder annotation, which can be found below:

%TC:ignore
\begin{lstlisting}[caption=Kubebuilder CEL annotation for enforcing mutual exclusivity between inline and git \texttt{Playbook} sources]
// +kubebuilder:validation:XValidation:rule="has(self.inline) != has(self.git)",message="Inline and Git are mutually exclusive"
\end{lstlisting}
%TC:endignore

Due to the mutual exclusivity between the \enquote{git} and \enquote{inline} fields, there are two fundamentally different ways in which an \anplaybook can be defined.
The first one is to declare the \texttt{Playbook} inline in the \anplaybook spec, embedding it directly into the manifest:

%TC:ignore
\begin{lstlisting}[language=yaml, caption=Example \anplaybook definition with inline source]
apiVersion: ansible-operator.lightjack.de/v1alpha1
kind: AnsiblePlaybook
metadata:
  name: inline-playbook
spec:
  inline:
    requirements: |
      roles:
        - name: geerlingguy.ntp
      collections:
        - name: ansible.posix
    playbook: |
      - name: Test install flow
        hosts: web_tier
        become: true

        roles:
          - geerlingguy.ntp

        tasks:
          - name: Set a sysctl value (ansible.posix)
            ansible.posix.sysctl:
              name: vm.swappiness
              value: '10'
              state: present

          - name: Tweak login banner perms (ansible.posix)
            ansible.posix.mount:
              path: /mnt/testtmp
              src: tmpfs
              fstype: tmpfs
              opts: size=16m
              state: mounted
\end{lstlisting}
%TC:endignore

This declares an example \texttt{Playbook} which has a dependency on one \texttt{Collection} and \texttt{Role}.
If this \texttt{Playbook} is referenced by an \anrecjob, it would be executed verbatim as written in the spec.

The other way to define an \anplaybook is to use an \gls{http} or \gls{https} git source for the \texttt{Playbook}.
That way, the git repository is cloned into the \texttt{Jobs} \texttt{Pod} and then the paths given are used to resolve dependencies and execute the \texttt{Playbook}:

%TC:ignore
\begin{lstlisting}[language=yaml, caption=Example \anplaybook definition with git source]
apiVersion: ansible-operator.lightjack.de/v1alpha1
kind: AnsiblePlaybook
metadata:
  name: http-git-playbook
spec:
  git:
    repo:
      url: http://git-server.default.svc.cluster.local/git/playbook-repo.git
    playbookPath: playbook.yml
    requirementsPath: dir/requirements.yml
\end{lstlisting}
%TC:endignore

\subsection{The \anrecjob resource}
The complete \anrecjob spec type declaration can be found in the appendix under section \ref{app:anrecjobdeclare}.
While the controller for this resource holds the most of the logic for the operator, the resource itself only holds two fields:

%TC:ignore
\begin{lstlisting}[language=yaml,caption=Example \anrecjob definition]
apiVersion: ansible-operator.lightjack.de/v1alpha1
kind: AnsibleReconcileJob
metadata:
  name: inline-reconcile-job
spec:
  schedule: "0 0 * * *"
  playbookRef:
    # ref to a playbook in the same namespace
    # host selection is handled via the inventory, and the group referenced in the playbook
    name: inline-playbook
\end{lstlisting}
%TC:endignore

In this case, this declares an \anrecjob that will execute every day at 0:00 and will execute the \enquote{inline-playbook} \anplaybook.

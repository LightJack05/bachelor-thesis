The following section outlines the implemented logic for the \glspl{crd} defined in the previous chapters.
Individual \glspl{crd} will be listed again and the reconcile logic for each object will be explained.
\anplaybook objects do not implement any logic and are therefore omitted here.

\subsection{Reconciling the \anhost resource}
As stated in the previous chapters, an \anhost needs to scan the \gls{ssh} host keys of the target machine.
Since reconcile logic should be idempotent, first there needs to be a check whether the \texttt{Secret} for the \gls{ssh} keys used to access the host exists.
If the \texttt{Secret} does not exist, the \anhost is requeued.

%TC:ignore
\begin{lstlisting}[language=go, caption=Checking whether the SSH key secret exists]
// Ensure the private key secret exists
privateKeySecretExists, err := r.hostPrivateKeySecretExists(ctx, &ansibleHost)
// [...] error handler omitted

if !privateKeySecretExists {
    // If the private key secret does not exist, we can log the error and requeue the request
    if err := r.setStatusNotReady(ctx, &ansibleHost, "PrivateKeySecretMissing", "The private key secret does not exist"); err != nil {
        // [...] error handler omitted
    }

    lg.Info("Private key secret does not exist, requeuing.")
    return ctrl.Result{RequeueAfter: 30 * time.Second}, nil
}
\end{lstlisting}
%TC:endignore

\clearpage
The called function obtains the \texttt{Secret} from the API and ensures that the key is present and parses as an \gls{ssh} private key:

%TC:ignore
\begin{lstlisting}[language=go, caption=Validating the host private key secret exists]
func (r *AnsibleHostReconciler) hostPrivateKeySecretExists(ctx context.Context, ansibleHost *ansibleoperatorv1alpha1.AnsibleHost) (bool, error) {
	secret := &corev1.Secret{}
	err := r.Get(ctx, client.ObjectKey{Namespace: ansibleHost.Namespace, Name: ansibleHost.Spec.SSH.SSHKeySecretRef.Name}, secret)
	if errors.IsNotFound(err) {
		return false, nil
	}
    // [...] error handler omitted

	keyData, ok := secret.Data[sshKeySecretKey]
	if !ok || len(keyData) == 0 {
		return false, fmt.Errorf("private key secret is missing 'ssh_key' data or it is empty")
	}

	if _, err := cryptoSSH.ParsePrivateKey(keyData); err != nil {
		return false, fmt.Errorf("failed to parse private key: %w", err)
	}

	return true, nil
}
\end{lstlisting}
%TC:endignore

If the \texttt{Secret} is invalid, the status condition \enquote{Ready} on the \anhost is set to \enquote{False}, and it is requeued.
Next, unless the \enquote{IgnoreHostKey} option is set, the host key needs to be created.
This is done by performing an \gls{ssh} key scan on the target host, which was accomplished using a custom reimplementation of the logic used by \enquote{ssh-keyscan} in Go, which can be found in the appendix under section \ref{app:sshkeyscan}.
Given that there may be several goroutines blocked on network \gls{io} while connections wait for a timeout, the parallelization level for this controller needs to be high.

%TC:ignore
\begin{lstlisting}[language=go, caption=Setting up the \anhost controller with 100 concurrent reconciles]
// SetupWithManager sets up the controller with the Manager.
func (r *AnsibleHostReconciler) SetupWithManager(mgr ctrl.Manager) error {
	return ctrl.NewControllerManagedBy(mgr).
		For(&ansibleoperatorv1alpha1.AnsibleHost{}).
		Owns(&corev1.Secret{}).
		Owns(&corev1.ConfigMap{}).
		Named("ansiblehost").
		// Run at most 100 concurrent reconciles.
		// The high number here is irrelevant, since the threads aren't CPU bound, but just blocked on network IO for the most time.
		WithOptions(controller.Options{MaxConcurrentReconciles: 100}).
		Complete(r)
}
\end{lstlisting}
%TC:endignore

Once the keyscan is complete, the keys are formatted into the format used by the \gls{ssh} \enquote{known\_hosts} file, and stored in a \texttt{Secret} owned by the \anhost.
Finally, the \anhost vars are stored in a \texttt{ConfigMap} and then the \enquote{Ready} condition of the \anhost is set to \enquote{True}.

\subsection{Reconciling the \angroup resource}
The reconcile cycle of the \angroup resource consists of a status check and ensuring the \texttt{ConfigMap} holding the \texttt{Group} variables exists.
First, all status conditions are set to \enquote{Unknown} on the resource, so they all exist, independently of where the reconcile loop terminates.

%TC:ignore
\begin{lstlisting}[language=go]
// Set all conditions to unknown if they are not set
if err := r.defaultStatusToUnknown(ctx, &group, ansibleoperatorv1alpha1.AnsibleGroupConditionHealthy); err != nil {
	return ctrl.Result{}, fmt.Errorf("failed to set condition on AnsibleGroup: %v", err)
}
if err := r.defaultStatusToUnknown(ctx, &group, ansibleoperatorv1alpha1.AnsibleGroupConditionReferencesValid); err != nil {
	return ctrl.Result{}, fmt.Errorf("failed to set condition on AnsibleGroup: %v", err)
}
if err := r.defaultStatusToUnknown(ctx, &group, ansibleoperatorv1alpha1.AnsibleGroupConditionReady); err != nil {
	return ctrl.Result{}, fmt.Errorf("failed to set condition on AnsibleGroup: %v", err)
}
\end{lstlisting}
%TC:endignore

\clearpage
Afterward, the variables \texttt{ConfigMap} is ensured to exist in the same way as it was for the \anhost resource.

%TC:ignore
\begin{lstlisting}[language=go, caption=Creating the \texttt{Group} variables \texttt{ConfigMap}]
cm = &v1.ConfigMap{
	ObjectMeta: metav1.ObjectMeta{
		Name:      group.Name + varsConfigMapSuffix,
		Namespace: group.Namespace,
	},
	Data: map[string]string{
		groupVarsConfigMapKey: vars,
	},
}
if err := ctrl.SetControllerReference(group, cm, r.Scheme); err != nil {
	return fmt.Errorf("failed to set owner reference for ConfigMap: %w", err)
}
if err := r.Create(ctx, cm); err != nil {
	return fmt.Errorf("failed to create ConfigMap for AnsibleGroup vars: %w", err)
}
\end{lstlisting}
%TC:endignore

\clearpage
If a resource with the target name exists, it is only updated if it is owned by the correct \angroup, so the contents reflect the current desired state.

%TC:ignore
\begin{lstlisting}[language=go, caption=Ensuring the \texttt{Group} variables \texttt{ConfigMap} content matches the desired state]
// Check the owner reference and update the vars if it is owned by the AnsibleGroup
if metav1.IsControlledBy(cm, group) {
	if cm.Data == nil {
		cm.Data = make(map[string]string)
	}
	if cm.Data[groupVarsConfigMapKey] != vars {
		cm.Data[groupVarsConfigMapKey] = vars
		if err := r.Update(ctx, cm); err != nil {
			return fmt.Errorf("failed to update ConfigMap for AnsibleGroup vars: %w", err)
		}
	}
} else {
	return fmt.Errorf("ConfigMap %s is not owned by AnsibleGroup %s", cm.Name, group.Name)
}
\end{lstlisting}
%TC:endignore

Finally, all subgroups and \texttt{Hosts} are iterated over and validated to make sure they resolve to proper Kubernetes objects and that they also have their \enquote{Ready} condition set to \enquote{True}.

\subsection{Reconciling the \anrecjob resource}
The \anrecjob resource has the most complex reconcile logic since it performs the most actions.
Firstly, the \anrecjob has three status conditions that need to be set:

\begin{itemize}
	\item{\textbf{Ready} indicates that the resource is ready to execute \texttt{Jobs}}
	\item{\textbf{Progressing} indicates that a \texttt{Job} is currently running}
	\item{\textbf{Successful} indicates that the last \texttt{Job} completed successfully}
\end{itemize}

When starting the reconcile loop, all of these conditions are set to \enquote{Unknown}.
Once that is complete, the inventory \texttt{ConfigMap} is templated.
First, all \anhost and \angroup resources are acquired from the API server and then stored in maps.
These maps are then used to build the inventory content, which can be found as a Go struct in the appendix under section \ref{app:invstruct}.

Unready \texttt{Hosts} and \texttt{Groups} will be shown as such, but will not be actioned by the \anrecjob, since these errors are not fatal to \texttt{Job} execution.
Meanwhile, an invalid generated inventory would be fatal to the execution of the entire \texttt{Job} and is therefore already recorded as an error while rendering the inventory.
Should any references in the data given to the operator not resolve properly, the operator will treat the entire inventory as invalid, and stop reconciliation while recording the unresolved reference in the \enquote{Ready} status message, and set its status to \enquote{False}.
It was decided not to silently skip problematic resources, since this would cause a silent failure and may lead to unexpected behavior.
Once the inventory is constructed into the struct, it is rendered using the template function in \ref{app:templatefunc} into a string which is then stored in a \texttt{ConfigMap}.

\clearpage
The known hosts file is created similarly, however, not from a template, but by simple string concatenation of the content of the \texttt{Secrets} in question.
Additionally, the runtime \texttt{ConfigMap}, which determines where to acquire the repository, files and similar data, is constructed from the data given in the\linebreak referenced \anplaybook.

With the configuration data built, the \texttt{CronJob} that will execute the \texttt{Playbooks} against the constructed inventory is built.
It gets several volume mounts, which are listed below.

\begin{itemize}
	\item{The inventory is mounted to \enquote{/inventory/hosts.yaml}}
	\item{The known\_hosts file is mounted to \enquote{/ssh/known\_hosts}}
	\item{The runtime \texttt{ConfigMap} mounts several keys into the following files under \enquote{/config}}
	      \subitem{\enquote{playbook.yaml} contains the \texttt{Playbook} to be executed}
	      \subitem{\enquote{requirements.yml} contains the requirements for the \texttt{Playbook}}
	\item{Additionally, the runtime \texttt{ConfigMap} also provides environment variables to the \texttt{Job} \gls{pod} which are used for Git-sourced \texttt{Playbooks}}
	      \subitem{\enquote{OPERATOR\_GIT\_REF} specifies which branch or tag to use in the repository}
	      \subitem{\enquote{OPERATOR\_GIT\_REPO\_URL} specifies the remote repository to clone}
	      \subitem{\enquote{OPERATOR\_GIT\_PLAYBOOK\_PATH} specifies the path of the \texttt{Playbook} within the repository}
	      \subitem{\enquote{OPERATOR\_GIT\_REQUIREMENTS\_PATH} specifies the path of the requirements file in the repository}
	\item{The \gls{ssh} private keys are mounted into the \enquote{/ssh} directory, using their Kubernetes object names as filenames}
	\item{The \texttt{Host} variable \texttt{ConfigMaps} are mounted into the \enquote{/inventory/host\_vars} directory, using the inventory \texttt{Host} names as filenames}
	\item{The \texttt{Group} variable \texttt{ConfigMaps} are mounted into the \enquote{/inventory/group\_vars} directory, using the inventory \texttt{Group} names as filenames}
\end{itemize}

Within the \texttt{CronJob} is one init container and one regular container defined.
Once the \texttt{CronJob} is constructed, it is server-side applied to the Kubernetes API server.
This both implicitly creates the object and also ensures that only the new configuration applied remains with no stale values.

Once the \texttt{CronJob} is created, the status conditions are updated to reflect the current state of the resource.
Every \anrecjob specifies its own name on \texttt{Jobs} belonging to it via a label on the resource.
This way, all \texttt{Jobs} belonging to the current \anrecjob are acquired from the API server and are then iterated over to find the one with the latest start time. Since the concurrency policy forbids concurrent execution, that \texttt{Job} is the only one that can be running.
If the \texttt{Job} is running according to its status block, the \enquote{Progressing} condition on the \anrecjob is set to \enquote{True}.
If no \texttt{Job} was found, the condition is set to \enquote{Unknown}.
Otherwise, the condition is set to \enquote{False}.
According to the same \texttt{Job}, the \enquote{Successful} condition is also set, depending on the success state of the \texttt{Job}.

During development, it has become clear that interpreting the logs Ansible outputs is largely unnecessary, since they are best read and interpreted by a human in the case of failures.
Outputting logs as \gls{json} and interpreting them in operator logic would allow for status reporting on objects, but may mask errors and make it harder to identify the \texttt{Tasks} that led up to an error.
Therefore, it has been decided to limit the status reporting of the \anrecjob to a basic success/failure state, and offload additional debugging capabilities to the logs of the relevant \texttt{Job}.
In existing platforms, logs can therefore be handled by existing infrastructure.
